P0: 明確な無駄・近傍生成の修正**
   - `src/precompute.rs` の `orientation_neighbors_for_block()` は、同じ変更後orientationについてIoUを昇順に並べてから`dedup`しています。結果として最も形状を維持しないオフセットが残ります。
     - IoU降順にして最大IoUを残すべきです。
     - Rotateは全試行の約41.5%を占めるため、影響が大きいです。
   - Globalの制約期間はSwapを約15.5%選択しますが、`src/solver/optimize.rs` で必ず`None`になります。
     - 制約期間だけSwap確率を0にするか、Bayと同じ「同一bay・precedence維持swap」を使用します。
   - 制約期間は近傍確率だけ`constrained_neighbor_params`を使い、探索幅などは`self.params`を使っています。選択したパラメータセットを近傍本体にも渡すべきです。
   - local bestごとの`eprintln!`は時間制限下の反復数を減らすため、通常実行では無効化した方がよいです。

2. **P0: 温度設定を改善する**
   - 現在の開始温度は概ね`0.01 * w1`です。遅れが1日悪化する遷移の受理率は
     ```text
     exp(-w1 / (0.01 * w1)) = exp(-100)
     ```
     となり、実質的に山登りです。
   - Bayは既定重みが同じ場合、開始`0.01`、終了`0.1`なので、時間経過とともに温度が上がっています。
   - まず以前の温度へ戻した上で、正のスコア差分をログ集計し、開始時受理率20〜50%、終了時1〜5%程度になるよう設定するのが安全です。
   - workerは「貪欲」「中温」「高温」に明確に分け、高温workerでは少なくとも一時的な1日悪化を現実的な確率で受理できるようにします。

3. **P1: Global探索をZ2/Z3指向にする**
   - 現在の近傍割合は、Shift約41.5%、Rotate約41.5%、Swap約15.5%に対し、単独でbayを変えられるMoveは約0.5%、LargeReconstructは約1%しかありません。
   - `try_move_neighbor()` の対象選択もZ1とZ3だけを見ており、Z2を無視しています。また、小面積ブロックを優先するため、大型blockerや高workloadブロックを動かしにくいです。
   - 次の目的別近傍を追加・強化するのが有効です。
     - 正規化load最大bayから最小bayへ、Z2差分が最も改善するブロックを移動。
     - preference penaltyが大きいブロックを、上位選好bayへ移動。
     - 移動先を塞ぐ少数ブロックも同時に削除して再構築。
   - まずはGlobalのMove比率を大きく上げ、候補選択に「Z2の正確な限界差分」「Z3改善量」「tardiness」を入れるのが小規模な改善です。

4. **P1: Z1向けに時間構造を組み替える**
   - 現在は各配置候補を基本的に最早時刻へ入れるため、急ぎブロックへ空間を譲る目的で、別ブロックを意図的に遅らせる操作が弱いです。
   - `doc/idea.md` のtargeted reconstructが有望です。
     1. tardinessが大きいブロックを選ぶ。
     2. `release_time`または`due_date - processing_time`への配置を試す。
     3. 空間・時間的に邪魔するブロックだけ削除する。
     4. 邪魔したブロックを再挿入する。
   - あわせて、他ブロックのENTRY/EXIT時刻を候補にするchange-entry-time近傍、Shiftの全方向化が有効です。
   - Bay annealingは抽象解の正のtardinessへ到達した時点で終了しますが、抽象解は最適下界ではありません。早期終了は原則`tardiness == 0`だけにした方が改善を取り逃しません。
   - precedence固定時間も長いため、Bay後半またはGlobalの早い段階で段階的に解除する価値があります。

5. **P2: 抽象解のモデル誤差と反復効率を改善する**
   - Preoptimizeは面積近似なので、抽象スコアが最良の1解と、実配置後に最良になる解が一致する保証はありません。
     - 「公式目的最良」「congestion込み最良」「異なるbay割当」の上位数解を保持。
     - それぞれ短時間で実配置化し、実スコア最良をBay/Globalへ渡す方法が有力です。
   - 全workerが同じ初期解から始まるため、温度差だけでなく初期解自体を分ける方が探索盆地を増やせます。
   - Preoptimizeは近傍ごとに`used_area`全体をcloneし、Globalもschedule cloneと全体スコア再計算を行います。変更区間だけのapply/undoやZ1/Z2/Z3の差分保持で反復数を増やせます。
   - Bayを常に全時間の30%使うのではなく、改善停止・近傍成功率・未達bay数を見てGlobalへ早期移行する方がよいです。
